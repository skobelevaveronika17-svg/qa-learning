Ветки, слияние, конфликты

35 минут · пять частей

1. Зачем ветки — на примере

Ты дизайнер, и ты это знаешь: когда пробуешь новый вариант макета, ты не правишь утверждённый, а делаешь копию страницы в Figma. Понравилось — переносишь. Не понравилось — удаляешь копию, оригинал цел.

Ветка в Git — то же самое для кода, только без ручного копирования.

Простыми словами

Ветка — отдельная линия коммитов. В ней можно делать что угодно, основная ветка main не меняется. Слияние (merge) — перенос коммитов из ветки обратно в main. Конфликт — когда в обеих ветках поменяли одну и ту же строку, и Git не знает, какую версию оставить.

main: A ── B ──────────── E \ / feature/emails: C ── D

A и B — коммиты в main. Ты создала ветку и сделала в ней C и D. В main за это время ничего не менялось — или появился коммит, это неважно. E — слияние: всё из C и D попало в main.

2. Команды для веток

[Бумага] Шесть команд
КомандаЧто делает
git branchПоказывает все ветки. Текущая — со звёздочкой
git switch -c имяСоздаёт ветку и сразу переходит в неё
git switch имяПереходит в существующую ветку
git merge имяВливает ветку имя в ту, в которой ты сейчас
git log --oneline --graphИстория коммитов, по одной строке, с рисунком веток
git branch -d имяУдаляет ветку, уже влитую в main

В старых инструкциях вместо switch пишут checkout: git checkout -b имя — то же, что git switch -c имя. Работают обе, на собеседовании могут спросить про checkout.

Главная ловушка merge

git merge feature/emails вливает feature/emails в текущую ветку. Поэтому сначала git switch main, потом merge. Если забыть и стоять в feature — main не изменится, а наоборот, main вольётся в feature.

Как называть ветки

Принято: тип и короткое описание через дефис. feature/bad-emails — новое, fix/password-length — исправление, test/login-cases — тесты. Латиница, без пробелов.

3. Два вида слияния

ВидКогдаЧто пишет Git
Fast-forward, перемоткаВ main ничего не менялось с момента создания ветки. Git просто передвигает main вперёд, на последний коммит веткиFast-forward
Merge commit, коммит слиянияВ main за это время появились свои коммиты. Git соединяет две линии новым коммитом. Откроется редактор для сообщения — оставь как есть и закройMerge made by the 'ort' strategy.

Ты увидишь оба вида в задании. Ни один не лучше другого, просто разные ситуации.

4. Конфликт и как его решить

Пример. В main строка в файле practice.md стала «Цель: QA engineer», а в ветке feature/b та же строка стала «Цель: strong junior к маю». Делаем merge:

$ git merge feature/b Auto-merging practice.md CONFLICT (content): Merge conflict in practice.md Automatic merge failed; fix conflicts and then commit the result.

Git вписал в файл обе версии и маркеры между ними:

<<<<<<< HEAD
Цель: QA engineer
=======
Цель: strong junior к маю
>>>>>>> feature/b
КусокЧто значит
<<<<<<< HEADНачало версии из ветки, где ты сейчас — из main
=======Разделитель
>>>>>>> feature/bКонец версии из ветки, которую вливаешь
[Бумага] Четыре шага решения конфликта
  1. Открыть файл, найти маркеры.
  2. Решить, что оставить: первую версию, вторую, или собрать из обеих. Если не знаешь — спросить автора другой ветки.
  3. Удалить все три маркера. В файле должен остаться только нормальный текст или код.
  4. git add файл, потом git commit. Передумала посреди — git merge --abort вернёт всё как было до merge.

PyCharm умеет показывать конфликт в три колонки с кнопками «взять слева» и «взять справа». Это удобно, но сегодня решай руками в тексте: так понятнее, что происходит.

5. .gitignore — что не должно попасть в репозиторий

Файл .gitignore в корне репозитория — список того, что Git не замечает. git add . эти файлы пропустит.

# настройки PyCharm
.idea/
# служебные файлы Python
__pycache__/
# пароли и ключи
.env
# виртуальное окружение — будет на неделе 6
venv/
Важно

.gitignore не убирает файлы, которые уже закоммичены. Он только не даёт добавить новые. Поэтому пароль Олега из истории не исчезнет — пароль меняют.

Ветка, слияние, конфликт — руками

35 минут · в твоём репозитории qa-learning

Перед началом
  1. Все сегодняшние и вчерашние файлы закоммичены и запушены. Проверь: git status должен сказать nothing to commit, working tree clean. Если нет — сначала закоммить.
  2. Узнай, как называется твоя основная ветка: git branch. Скорее всего main, но может быть master. Если master — везде ниже пиши master вместо main.

Часть 1 · Ветка и fast-forward · 10 минут

  1. Создай ветку и перейди в неё: 
    git switch -c practice/branches
    Git ответит Switched to a new branch 'practice/branches'.
  2. Создай файл notes/git-practice.md с одной строкой: Цель: middle Automation QA. Закоммить: 
    git add notes/git-practice.md
git commit -m "Практика веток: файл с целью"
  3. Вернись в main и посмотри: файла notes/git-practice.md в папке нет. Это нормально — он живёт в ветке. 
    git switch main
  4. Влей ветку: 
    git merge practice/branches
    Git ответит Fast-forward — файл появился в main.
  5. Посмотри историю: git log --oneline --graph -5. Перепиши первую строку вывода в тетрадь.

Часть 2 · Нарочный конфликт · 20 минут

  1. Создай вторую ветку от main: 
    git switch -c practice/conflict
  2. В notes/git-practice.md замени строку на Цель: strong junior к маю 2027. Закоммить: 
    git commit -am "Цель в ветке"
  3. Вернись в main: git switch main. В том же файле замени ту же строку на Цель: Automation QA. Закоммить: 
    git commit -am "Цель в main"
    Теперь одна строка изменена по-разному в двух ветках — конфликт гарантирован.
  4. Влей ветку: 
    git merge practice/conflict
    Git напишет CONFLICT. Не пугайся, это и было целью. Сделай скриншот этого вывода.
  5. Выполни git status и прочитай, что пишет Git. Найди там строку both modified.
  6. Открой файл. Оставь одну строку: Цель: strong junior к маю 2027, затем middle Automation QA. Удали все три маркера.
  7. Заверши слияние: 
    git add notes/git-practice.md
git commit -m "Решён конфликт в цели"
  8. Посмотри граф: git log --oneline --graph -6. Найди место, где две линии сходятся. Сделай скриншот.
  9. Удали практические ветки и отправь main: 
    git branch -d practice/branches practice/conflict
git push

Часть 3 · .gitignore · 5 минут

  1. Проверь, есть ли в корне репозитория файл .gitignore. Если нет — создай.
  2. Добавь в него строки: .idea/, __pycache__/, .env, venv/ — каждая с новой строки.
  3. Проверь, не закоммичена ли уже папка .idea: открой репозиторий на GitHub. Если она там есть — напиши мне, уберём её завтра одной командой, сегодня не трогай.
  4. Закоммить .gitignore и сделай push.
Готово, когда на GitHub в main лежит notes/git-practice.md с решённым конфликтом, лишних веток нет, есть .gitignore, и у тебя два скриншота: CONFLICT и граф.
Если что-то пошло не так
  • Запуталась посреди конфликта — git merge --abort, всё вернётся как было до merge. Начни шаг 4 части 2 заново.
  • Открылся непонятный редактор с текстом коммита (бывает при merge commit) — это редактор Vim. Нажми Esc, напечатай :wq и Enter.
  • Git пишет «error: Your local changes would be overwritten» при switch — есть незакоммиченные изменения. Сначала закоммить их.
  • Ничего из этого не помогло — сделай скриншот терминала и пришли мне. Не делай --force и не удаляй папку.

Невалидные email — в отдельной ветке

60 минут · новый файл python/day21_emails.py

Генератор умеет делать пароли для всех классов, а email — только правильные. Сегодня добавляем невалидные email для требования 3.3 — и делаем это так, как в команде: в своей ветке, потом слияние в main.

Шаг 0 · Ветка · 2 минуты

git switch -c feature/bad-emails

Весь код ниже пишешь и коммитишь в этой ветке.

Разобранный пример — выбор по словарю вместо цепочки if

Функция возвращает текст для статус-кода. Можно написать пять if, а можно положить варианты в словарь и достать нужный через get:

def status_text(code):
    texts = {200: "OK", 401: "Не авторизован", 404: "Не найдено"}
    return texts.get(code)

print(status_text(200), status_text(404), status_text(500))
# OK Не найдено None
ВызовЧто происходитРезультат
status_text(200)Ключ 200 есть в словаре"OK"
status_text(404)Ключ 404 есть"Не найдено"
status_text(500)Ключа нет, get без второго аргумента возвращает NoneNone
Простыми словами

Если выбор — «по названию взять готовое значение», словарь короче и понятнее цепочки if. Добавить новый вариант — одна строка в словаре.

Шаг 1 · make_bad_email · 20 минут

Скопируй make_email из генератора. Напиши make_bad_email(name, kind): по виду ошибки kind возвращает невалидный email, неизвестный вид — None.

kindЧто за ошибкаДля name="anna" вернуть
"noat"нет @annatest.ru
"twoat"два @anna@@test.ru
"nodomain"нет доменаanna@
"space"пробел внутриanna @test.ru
"spaces"только пробелы, name не используется" " (три пробела)

Проверки — скопируй в конец файла. Должно быть шесть True:

print(make_bad_email("anna", "noat") == "annatest.ru")
print(make_bad_email("anna", "twoat") == "anna@@test.ru")
print(make_bad_email("anna", "nodomain") == "anna@")
print(make_bad_email("anna", "space") == "anna @test.ru")
print(make_bad_email("anna", "spaces") == "   ")
print(make_bad_email("anna", "unknown") is None)
Подсказка

Внутри функции — словарь, где ключи — виды ошибок, а значения — готовые строки через f-строки: "noat": f"{name}test.ru". В конце — return variants.get(kind), как в примере.

Когда все True — закоммить в ветке: git add python/day21_emails.py и git commit -m "make_bad_email: невалидные email по видам".

Шаг 2 · Проверка всех email разом · 25 минут

Функцию проверки email я даю готовой — это упрощённая версия того, что делает форма по требованиям 3.1 и 3.3. Скопируй её в файл как есть:

def check_email(email):
    if email.strip() == "":
        return "Заполните поле"
    if email.count("@") != 1:
        return "Неверный формат email"
    if " " in email:
        return "Неверный формат email"
    domain = email[email.index("@") + 1:]
    if domain == "" or "." not in domain:
        return "Неверный формат email"
    return "OK"
СтрокаЧто проверяет
email.strip() == ""Пусто или одни пробелы — 3.1
email.count("@") != 1count считает, сколько раз символ встречается. Ни одного или два — ошибка
email.index("@") + 1index — номер позиции @. Срез с позиции после @ до конца — это домен
"." not in domainВ домене нет точки: anna@test — ошибка
